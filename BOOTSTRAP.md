# Bootstrap Guide — ZenControl TPI MCP Server

This document captures architectural decisions and lessons learned from the
`zencontrol-cloud-mcp` implementation and translates them into a concrete
starting point for the ZenControl Third-Party Interface (TPI) MCP server.

Read this before writing any code. The coding agent that picks this up should
treat it as its primary specification.

---

## 1. Context: Cloud MCP vs TPI MCP

| Dimension            | `zencontrol-cloud-mcp`                      | `zencontrol-tpi-mcp` (this project)          |
|----------------------|---------------------------------------------|----------------------------------------------|
| Transport            | HTTPS REST + WSS (WebSocket)                | Persistent TCP socket (JSON framing)         |
| Authentication       | OAuth 2.0 + PKCE, encrypted token cache     | Static API key in every request              |
| Topology             | Cloud → any site globally                   | Direct LAN → single controller               |
| Deployment model     | stdio (local) or streamable-http (hosted)   | stdio (local) only, initially                |
| Python HTTP library  | `httpx.AsyncClient`                         | `asyncio.open_connection` (raw TCP)          |
| Live/events          | WebSocket subscription                      | Long-lived subscription via same TCP socket  |
| Multi-user           | Supported via bearer-token pass-through     | Not needed initially (single user, LAN)      |

The TPI connects **directly to a controller on the local network**, so there is
no OAuth, no cloud round-trip, and no token refresh dance. The trade-off is that
you own connection management (reconnect, keep-alive, framing).

## 3. TCP Client Architecture

This is the biggest structural difference from the cloud implementation.

### Why a persistent connection

The TPI keeps a **single persistent TCP connection** open to the controller.
Opening and tearing down a new TCP socket per command adds unacceptable latency
and may exhaust controller connection limits.

### Framing convention

The TPI uses **newline-delimited JSON** (one JSON object per line). Every
message — both requests and responses — is a single JSON object terminated by
`\n`. Use `asyncio.StreamReader.readline()` for reading.

```
→ {"command": "getGroups", "apiKey": "...", "requestId": "abc123"}\n
← {"requestId": "abc123", "result": "success", "groups": [...]}\n
```

> **Confirm the exact framing with ZenControl TPI documentation.** If the
> protocol uses length-prefixed framing instead, adapt `client.py` accordingly.

### `client.py` skeleton

```python
"""Persistent async TCP client for the ZenControl TPI."""

from __future__ import annotations

import asyncio
import json
import logging
import uuid
from typing import Any

logger = logging.getLogger(__name__)


class ZenControlTPI:
    """Async persistent TCP client for the ZenControl Third-Party Interface.

    Maintains a single connection. Automatically reconnects on disconnect.
    Request/response matching is done via a ``requestId`` field.
    """

    def __init__(self, host: str, port: int, api_key: str) -> None:
        self._host = host
        self._port = port
        self._api_key = api_key
        self._reader: asyncio.StreamReader | None = None
        self._writer: asyncio.StreamWriter | None = None
        self._pending: dict[str, asyncio.Future] = {}
        self._read_task: asyncio.Task | None = None

    async def connect(self) -> None:
        """Open the TCP connection and start the read loop."""
        self._reader, self._writer = await asyncio.open_connection(
            self._host, self._port
        )
        self._read_task = asyncio.create_task(self._read_loop())
        logger.info("Connected to TPI at %s:%s", self._host, self._port)

    async def close(self) -> None:
        """Close the TCP connection and cancel the read loop."""
        if self._read_task:
            self._read_task.cancel()
        if self._writer:
            self._writer.close()
            await self._writer.wait_closed()

    async def _read_loop(self) -> None:
        """Continuously read lines from the socket and dispatch responses."""
        assert self._reader is not None
        try:
            while True:
                line = await self._reader.readline()
                if not line:
                    break
                try:
                    msg = json.loads(line.decode())
                    request_id = msg.get("requestId")
                    if request_id and request_id in self._pending:
                        self._pending[request_id].set_result(msg)
                except json.JSONDecodeError:
                    logger.warning("Received non-JSON line: %r", line)
        except asyncio.CancelledError:
            pass
        except Exception as exc:
            logger.error("Read loop error: %s", exc)
            # Fail all pending futures on disconnect
            for fut in self._pending.values():
                if not fut.done():
                    fut.set_exception(exc)

    async def send(self, command: str, **params: Any) -> dict:
        """Send a TPI command and await the matching response."""
        request_id = str(uuid.uuid4())
        payload = {
            "command": command,
            "apiKey": self._api_key,
            "requestId": request_id,
            **params,
        }
        assert self._writer is not None
        loop = asyncio.get_event_loop()
        fut: asyncio.Future[dict] = loop.create_future()
        self._pending[request_id] = fut
        self._writer.write((json.dumps(payload) + "\n").encode())
        await self._writer.drain()
        try:
            return await asyncio.wait_for(fut, timeout=30.0)
        finally:
            self._pending.pop(request_id, None)
```

### Key design decisions (from cloud implementation learnings)

1. **Per-token response cache** — The cloud client cached GET responses keyed by
   a hash of the user's token. The TPI has no cache concern (LAN latency is
   negligible and the TPI pushes state changes). Keep `commands.py` simple.

2. **Rate limiting** — The cloud client enforced 10 RPS. For TPI, rate limiting
   is typically unnecessary on LAN. Add it only if the controller docs indicate
   one is needed.

3. **Retry logic** — The cloud client retried 401/429/5xx. For TPI:
   - Auth failure (bad key) → fail fast, do not retry.
   - Timeout → retry once after reconnect.
   - Connection dropped → reconnect transparently in `connect()`.

4. **Token/auth caching** — Not applicable. The API key is static and lives in
   `self._api_key`.

## 4. Authentication

The TPI uses a **static API key**, not OAuth. This simplifies `server.py`
dramatically — no browser redirect, no PKCE, no token refresh.

```python
# server.py — lifespan
async def _lifespan(server: FastMCP):
    host = os.environ.get("ZENCONTROL_TPI_HOST", "")
    port = int(os.environ.get("ZENCONTROL_TPI_PORT", "52100"))
    api_key = os.environ.get("ZENCONTROL_TPI_API_KEY", "")

    missing = [k for k, v in [
        ("ZENCONTROL_TPI_HOST", host),
        ("ZENCONTROL_TPI_API_KEY", api_key),
    ] if not v]
    if missing:
        raise SystemExit(f"Required env vars not set: {', '.join(missing)}")

    tpi = ZenControlTPI(host=host, port=port, api_key=api_key)
    await tpi.connect()
    try:
        yield {"tpi": tpi, "scope": ScopeConstraint()}
    finally:
        await tpi.close()
```

**No `auth/` module is needed** (drop the entire `auth/` package from the
cloud implementation). The `cryptography` and `platformdirs` dependencies are
also not needed.

## 6. Pydantic Models (`models/schemas.py`)

Mirror the structure from the cloud implementation but adapt to TPI's data
shapes. Key patterns to carry over:

### Tolerant field parsing

The cloud API sometimes returned label fields as either a string or a wrapped
object `{"value": "..."}`. Build your models to handle both shapes using
`model_validator`:

```python
from pydantic import BaseModel, model_validator

class LabelField(BaseModel):
    value: str | None = None

    @model_validator(mode="before")
    @classmethod
    def _coerce_string(cls, v):
        if isinstance(v, str):
            return {"value": v}
        return v
```

### Enum-as-string

Use `StrEnum` for all enumerated values so they serialise cleanly:

```python
from enum import StrEnum

class CommandType(StrEnum):
    OFF = "off"
    SET_LEVEL = "setLevel"
    RECALL_SCENE = "goToScene"
    ...
```

### Pydantic config

Add `model_config = ConfigDict(populate_by_name=True)` globally so that both
camelCase JSON keys and snake_case Python attributes work.

```python
        return None
    result = await ctx.elicit(
        f"This will {action} all lights in {scope}. Proceed?",
        response_type=bool,
        response_title="Confirm",
    )
    ...
```

## 8. MCP Resources

MCP resources expose read-only data as addressable URIs that LLM clients can
fetch without a tool call. Port the `resources/hierarchy.py` pattern:

```python
@mcp.resource(
    "zencontrol-tpi://groups",
    name="ZenControl Groups",
    description="All lighting groups on the connected controller.",
    mime_type="text/plain",
)
async def groups_resource(ctx: Context) -> str:
    tpi: ZenControlTPI = ctx.lifespan_context["tpi"]
    ...
```

Suggested URI scheme:

```
zencontrol-tpi://info              → controller info / firmware version
zencontrol-tpi://groups            → all groups
zencontrol-tpi://groups/{id}       → single group detail
zencontrol-tpi://devices           → all devices
zencontrol-tpi://scenes            → all scenes
```

## 9. Scope Constraint

Port `scope.py` from the cloud implementation with minimal changes. The TPI
MCP connects to a single controller, so the scope constraint is simpler —
instead of locking to a site UUID, lock to a **group prefix** or leave it as
a runtime no-op initially.

The full `ScopeConstraint` class (with `set_site`, `validate_site`,
`validate_target`) is still worth keeping for forward compatibility with
multi-controller setups.

## 10. Testing Strategy

### Mock the TCP layer

Instead of `respx` (which mocks `httpx`), write a minimal asyncio TCP mock:

```python
# tests/conftest.py
import asyncio, json
import pytest

class FakeTPI:
    """Minimal in-process TPI fake for testing."""

    def __init__(self):
        self._responses = {}

    def set_response(self, command: str, response: dict):
        self._responses[command] = response

    async def send(self, command: str, **params) -> dict:
        if command not in self._responses:
            raise ValueError(f"No fake response for command: {command}")
        return self._responses[command]

@pytest.fixture
def fake_tpi():
    return FakeTPI()
```

### Test tool outputs directly

```python
@pytest.mark.asyncio
async def test_list_groups_returns_formatted_string(fake_tpi, mcp_context):
    fake_tpi.set_response("getGroups", {
        "result": "success",
        "groups": [{"id": "1", "label": "Office"}],
    })
    result = await list_groups(mcp_context, scope_type="controller", scope_id="main")
    assert "Office" in result
    assert "1 group" in result
```

### Test the TCP client in isolation

Test `ZenControlTPI.send()` using `asyncio.StreamReader`/`StreamWriter` fakes
rather than a live controller.

## 14. Lessons Learned from Cloud Implementation

### What worked well — carry forward

1. **`register(mcp)` pattern in each `tools/*.py`** — Keeps tools grouped by
   domain, avoids a bloated `server.py`, and makes it easy to add or disable
   entire domains.

2. **Three-layer API separation** — `client.py` (transport), `commands.py`
   (typed API methods), `server.py`/tools (MCP presentation). Never let tools
   call transport directly.

3. **Lifespan context dict** — Passing `api`, `scope`, `live` via
   `ctx.lifespan_context` keeps tools testable (inject fakes in tests).

4. **Scope constraint object** — Simple single-responsibility class that
   validates IDs. Centrally enforced via `get_scope_constraint(ctx)`.

5. **Formatted string returns** — LLMs work much better with bullet-list
   output than with raw JSON. Always format in the tool layer.

6. **`parse_requested_properties` / `wants_property` helpers** — Let callers
   ask for specific fields, which keeps responses concise. Very useful for
   LLM token budget management.

7. **`confirm_broad_command` elicitation** — FastMCP's `ctx.elicit()` provides
   a natural safety gate for commands that affect many devices. Use it.

8. **Explicit `model_config = ConfigDict(populate_by_name=True)`** — Saves
   hours of debugging camelCase vs snake_case mismatches in API responses.

9. **Tolerant label models** (`{"value": "..."}` or `"..."`)  — Real-world APIs
   are inconsistent. Defensive Pydantic `model_validator` on common fields
   prevents surprising `ValidationError` crashes in production.

### What to do differently for TPI

1. **No OAuth complexity** — The `auth/` package is the most complex part of the
   cloud implementation. The TPI's static API key replaces all of that. Enjoy
   the simplicity.

2. **Connection management is now your responsibility** — httpx handled
   connection pooling transparently. With raw asyncio TCP you must implement
   reconnect, keepalive, and pending-future cancellation on disconnect yourself.
   Write a solid `_read_loop` with error handling before anything else.

3. **No HTTP response cache** — The cloud client cached GET responses per-token.
   The TPI is on LAN and the controller pushes state changes, so a TTL cache
   would be stale immediately. Skip it.

4. **`requestId` correlation is critical** — Because you use a persistent
   connection with potential concurrent tool calls, every request needs a UUID
   `requestId` and the read loop must route responses to the correct waiting
   coroutine. This is the `_pending: dict[str, asyncio.Future]` pattern in the
   client skeleton above.

5. **`asyncio.wait_for` timeout** — Always wrap the `await fut` with
   `asyncio.wait_for(fut, timeout=30.0)` so a non-responsive controller doesn't
   hang a tool call indefinitely.

6. **Startup validation** — The cloud implementation called `api.list_sites()`
   at startup to validate credentials. Do the same with a lightweight TPI
   `getInfo` or `ping` command to fail fast on misconfiguration.

## 15. Recommended Build Order

Work through these in sequence. Each step is independently testable.

1. **Scaffold project** — `pyproject.toml`, `src/` layout, `uv sync`, `.env.example`
2. **TCP client** — `api/client.py` with connect/send/close + read loop
3. **Client tests** — Mock the asyncio streams; test requestId routing and timeout
4. **Pydantic models** — `models/schemas.py` for core TPI response types
5. **`commands.py`** — Typed wrapper methods over `client.send()`
6. **`scope.py`** — Port `ScopeConstraint` unchanged
7. **`server.py`** — Lifespan + FastMCP setup + `main()`
8. **`tools/sites.py`** — List controller info (smoke test for end-to-end wiring)
9. **`tools/devices.py`** — `list_groups`, `list_devices`
10. **`tools/control.py`** — `control_light`, `set_colour`
11. **`tools/status.py`** — Query current levels / sensor states
12. **`tools/scope.py`** — `set_scope`, `get_scope`, `clear_scope`
13. **`resources/hierarchy.py`** — URI-addressable hierarchy resources
14. **`.vscode/mcp.json`** — Hook up to VS Code for live testing
15. **CI** — Copy workflows from cloud implementation, update package names
